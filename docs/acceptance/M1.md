### Protected-read negative control (Issue #7 comment 5653567880)

The proof target is P = `/myshop/index.html` (마이쇼핑). Every proof reads the **same P** twice.

| Request to P | Transport | HTTP status | Classification | Marker names observed |
| --- | --- | --- | --- | --- |
| Without any session (`CONTROL_READ`) | HTTP | **200** | **LOGIN_REQUIRED** | `state_logoff`, `login_check_redirect` |
| With the authenticated session (`PROTECTED_READ`) | HTTP | 200 | **AUTHENTICATED** | `state_logon`, `logout_action`, plus the informational `member_modify_link` |

What this shows:

- **HTTP 200 is not the proof.** The unauthenticated request is answered with 200, and the `xans-myshop` page skeleton is present even then.
- **The verdict comes from the server-rendered markers.** Without a session the logged-off module and the login-check redirect are present. With the session the logged-on module and the member logout action are present together.
- **The target is genuinely authentication-gated.** The same P, read without and with the session, falls on opposite sides of the proof. That held in every one of the 4 proofs of this run.
- **The first real login confirmed the ADR-0007 predicate hypothesis.** Its markers were a hypothesis based on the Cafe24 convention; the logged-in page shows the logged-on module together with the logout action.
- **Only marker names were recorded.** No page content was stored.

### Secret scan (counts only, five encodings)

Every real session generation of the run is scanned, as review `5191372031` blocker 3 and comment `5654655305` require.

**Values scanned** — all held in this process's memory only, and dropped at the end:

| Values | Count | Source |
| --- | --- | --- |
| Login | 2 | the ID and the password, read from the one OS secret-store record |
| Session generation **A** (first login; runs 1–2) | 6 | kept in memory **before** the forced expiry overwrote it |
| Session generation **B** (re-authentication; run 3) | 6 | decrypted in memory after run 3 |

Within each generation, every cookie value of at least 6 characters is scanned. Shorter values are flags too short to identify a session, so the scan skips them to avoid false positives.

**Artifacts** — **12 files**, produced across run 1, run 2 and run 3:

- the data directory: `icbm.db` with its WAL/SHM files (canonical tables and audit payloads), `logs/**`, and `sessions/*.enc`;
- the output directory: all three server logs, and the evidence file itself. The evidence file is written before the scan so that it is covered, and it is re-scanned once more after its final write.

**Encodings:** raw text (UTF-8, UTF-16-LE, CP949), URL encoding, JSON escaping, Base64 (standard and URL-safe, at every byte alignment) and HTML entities.

**Result: 0 hits across the whole matrix**, 14 values × 5 encoding families:

| Values | raw | url | json | base64 | html |
| --- | --- | --- | --- | --- | --- |
| `username`, `password` | 0 | 0 | 0 | 0 | 0 |
| `session_A:` ECSESSID, PHPSESSVERIFY, login_provider_1, wish_id, fb_external_id, fb_event_id | 0 | 0 | 0 | 0 | 0 |
| `session_B:` the same six cookies | 0 | 0 | 0 | 0 | 0 |

**The scanner discloses nothing itself:**

- Only labels (cookie names) and counts are recorded.
- A report that would carry a value in any encoding is refused, and the refusal names no value.
- A scan error fails the step, reporting only the exception type.
- No temporary file is written.
