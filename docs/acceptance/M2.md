# M2 — SmartStore CONNECT: acceptance plan

- Status: **DESIGN / NOT YET ACCEPTED**
- Milestone: M2 SmartStore CONNECT
- Provider: NAVER SmartStore / Commerce API
- Contract bundle: `docs/platforms/smartstore/`
- Acceptance authority: this document plus the owning SmartStore contracts
- Runtime implementation: Claude Code
- Architecture/audit: ChatGPT + independent cross-audit

M2 acceptance proves CONNECT. It does **not** prove SmartStore product registration.

The acceptance model is deliberately split by evidence kind instead of one flat checklist.

```text
1. Contract invariants      -> mock/unit/repository evidence
2. Provider measurements    -> R0, real authorized account, tightly budgeted
3. Operator attestation     -> A0, local handling only, SmartStore network I/O = 0
4. Regression floor         -> M0 + M1 + single-data-dir ownership remain intact
```

The design goal is to minimize real-provider calls. Development and failure injection use fakes/mocks first. Real SmartStore calls happen only after all local/static gates are green.

The milestone boundary is intentionally narrower than full long-horizon contract verification:

`M2 ACCEPTED != every SmartStore owning contract verified_at complete`

---

## 1. Evidence classes

### 1.1 `R0 = MEASURED_RUNTIME_EVIDENCE`

R0 means ICBM measured provider/runtime behavior against an authorized real SmartStore account.

Required M2 R0 slots:

- `SMARTSTORE-R0-TOKEN`
- `SMARTSTORE-R0-SELLER-ACCOUNT`
- `SMARTSTORE-R0-FIRST-TOKEN-CRASH`

Long-horizon/non-gating R0 slots:

- `SMARTSTORE-R0-TOKEN-REISSUE-WINDOW`
  - `status=DEFERRED_LONG_HORIZON` when the separate long-horizon observation session has not yet run;
  - `required_for_m2_acceptance=false`;
  - its measurement remains required for full AUTH contract verification and persistence-policy review.
- `SMARTSTORE-R0-APP-REAUTH`
  - `status=BLOCKED_BY_TIME` until a real/provider-supported machine-visible application re-auth condition can be observed;
  - `required_for_m2_acceptance=false`;
  - `APPLICATION_REAUTH_REQUIRED` remains schema-reserved and automatic detection remains disabled while this slot is unaccepted.

Therefore all of the following may simultaneously be true:

```text
M2 status = ACCEPTED
SMARTSTORE-R0-TOKEN-REISSUE-WINDOW = DEFERRED_LONG_HORIZON
SMARTSTORE-R0-APP-REAUTH = BLOCKED_BY_TIME
AUTH.md verified_at = null
```

### 1.2 `A0 = OPERATOR_ATTESTED_EVIDENCE`

A0 is not provider-measured runtime truth.

M2 defines:

- `SMARTSTORE-A0-PERMISSION`

This slot proves that ICBM correctly handles an operator attestation as limited-strength evidence. It does **not** prove that NAVER exposes machine-readable permission truth.

Core invariant:

`operator attestation != machine-verified provider truth`

Evidence-taxonomy migration is complete:

- `SMARTSTORE-A0-PERMISSION` is separated into the A0 evidence class by PR #21;
- the old name `SMARTSTORE-R0-PERMISSION` has been removed from `SOURCES.md` and `CAPABILITY_MAPPING.md`;
- A0 evidence cannot be promoted to R0 without a distinct provider measurement.

## 2. Overall M2 acceptance gate

M2 may be marked **ACCEPTED** only when all of the following are true:

1. every required contract invariant in §3 passes;
2. `SMARTSTORE-A0-PERMISSION` passes every handling/invalidation check in §4;
3. the three required M2 R0 slots in §5 are measured and accepted;
4. `SMARTSTORE-R0-APP-REAUTH` is explicitly `BLOCKED_BY_TIME` with `required_for_m2_acceptance=false`, unless a separately reviewed later measurement has already accepted it;
5. `SMARTSTORE-R0-TOKEN-REISSUE-WINDOW` is explicitly `DEFERRED_LONG_HORIZON` with `required_for_m2_acceptance=false`, unless a separately reviewed long-horizon session has already accepted it;
6. the main-campaign real-account call budget in §6 is not exceeded;
7. zero unadopted SmartStore endpoint calls occur;
8. M2 product write remains `UNVERIFIED` throughout;
9. regression floor §8 passes;
10. secret/evidence sanitization checks pass;
11. every acceptance result links to its evidence artifact/record.

No single R0/A0 slot automatically verifies another contract.

Neither A0 acceptance nor M2 acceptance may populate `PERMISSIONS_SCOPES.md verified_at`; that field remains `null` while `NO_MACHINE_READABLE_PERMISSION_SOURCE` applies under `SOURCES.md`.

## 3. Layer 1 — contract invariant acceptance

These checks are primarily mock/unit/integration/repository tests and must consume **zero real SmartStore calls**.

| ID | Acceptance invariant | PASS condition |
| --- | --- | --- |
| G1 | `auth != READY -> write != READY` | every non-READY auth fixture rejects `write=READY` |
| G2 | `AUTH_MISMATCH -> REVIEW_REQUIRED/AUTHENTICATION` | no auto-rebind; no fabricated PAUSED reason |
| G3 | `write_scope=MISSING -> write=BLOCKED + PAUSED/PRODUCT_REGISTRATION/SCOPE_INSUFFICIENT` | exact scoped convergence |
| G4 | `write_scope=UNKNOWN != SCOPE_INSUFFICIENT` | UNKNOWN never becomes missing without positive evidence |
| G5 | `write_scope=READY != write=READY` | scope proof alone cannot promote write |
| G6 | `endpoint=NOT_ADOPTED -> network I/O forbidden` | rejection happens before transport handoff |
| G7 | M2 product endpoints NOT_ADOPTED -> product write UNVERIFIED | no M2 path can promote product write |
| G8 | `contract_freshness=STALE` preserves existing runtime truth and blocks expansion | existing proven CONNECT stays usable; new trust/adoption is denied |
| G9 | `contract_freshness=REVIEW_REQUIRED` stops behavior depending on disputed invariant | affected automatic operation stops |
| G10 | `workflow_state=PAUSED` requires frozen reason and frozen scope | invalid reason/scope rejected |
| G11 | `workflow_state=REVIEW_REQUIRED` does not fabricate PAUSED reason | `reason_code=null` unless independently PAUSED |
| G12 | `error_class` does not authorize replay | retry/replay remains operation/outcome gated |
| G13 | `remote_outcome=UNKNOWN -> blind mutation replay forbidden` | reconcile/review path only |
| G14 | old credential/session-generation evidence cannot establish current auth READY | stale generation rejected |
| G15 | old application fingerprint/mapping revision makes permission evidence UNKNOWN | stale/mismatched permission evidence cannot remain READY |

Additional convergence tests required by the frozen contract:

- `workflow_scope` accepts only `AUTHENTICATION` and `PRODUCT_REGISTRATION` in M2;
- operator-attested permission uses the limited-strength semantic/icon (`◐`), not strong (`●`);
- persisted READY loses to current evidence after restart;
- generic `GW.AUTHN` does not directly map to `SCOPE_INSUFFICIENT` or `APPLICATION_REAUTH_REQUIRED`;
- before `SMARTSTORE-R0-APP-REAUTH` is accepted, suspected app re-auth converges to `REVIEW_REQUIRED/AUTHENTICATION/reason_code=null`.

## 4. Layer 2 — A0 operator-attestation acceptance

### `SMARTSTORE-A0-PERMISSION`

**Evidence kind:** `OPERATOR_ATTESTED_EVIDENCE`

**Real SmartStore network budget:** exactly **0 calls**.

This acceptance proves ICBM handling of operator evidence, not NAVER provider behavior.

PASS requires all of the following:

1. operator attestation input is persisted with `evidence_strength=OPERATOR_ATTESTED`;
2. evidence source/provenance, `observed_at`, application fingerprint, required groups, observed groups and mapping revision are retained;
3. UI/API renders positive operator evidence with `◐`, never `●`;
4. attestation alone cannot set `write=READY`;
5. application-fingerprint mismatch deterministically demotes `write_scope` to `UNKNOWN`;
6. required-group or endpoint-mapping revision change invalidates the prior attestation and converges to `UNKNOWN` until fresh evidence exists;
7. configured evidence freshness expiry converges to `UNKNOWN`;
8. an incomplete/malformed attestation cannot become READY;
9. save/read-back/invalidation survives process restart;
10. saving, validating, invalidating or displaying the attestation performs **zero SmartStore network calls**;
11. no product endpoint is probed "for confirmation";
12. exported/logged evidence contains no full `client_id`, secret, token or unrelated PII.

The fingerprint-mismatch test must use controlled local data by changing the configured application/client identity and proving that old attestation evidence cannot follow the new application.

`SMARTSTORE-A0-PERMISSION = ACCEPTED` does not make `PERMISSIONS_SCOPES.md verified_at` non-null. It verifies attestation handling only.

## 5. Layer 3 — provider-measured R0 acceptance

R0 acceptance separates **measurement completion** from **whether the observed result matches current documentation**.

For observational slots:

`trustworthy measurement completed = PASS for measurement`

while:

`measured behavior contradicts adopted P0/P1 contract = MEASURED_CONTRACT_REVIEW_REQUIRED`

A provider contradiction is not rewritten into a fake expected PASS result and is not automatically classified as an implementation failure.

### 5.1 `SMARTSTORE-R0-TOKEN`

Required proof:

- one real authorized `SMARTSTORE_AUTH_TOKEN` call;
- exact SELF request shape (`grant_type=client_credentials`, `type=SELF`, no `account_id`);
- HTTP/JSON/success predicate evaluated;
- Bearer token type understood;
- observed `expires_in` and latency recorded without logging bearer value;
- candidate response becomes current only after durable session commit.

Implementation errors, malformed requests, secret leakage, wrong endpoint, redirect-follow, or success-predicate bypass are FAIL.

Provider values that differ from current documented expectations are recorded and trigger contract review rather than being silently normalized.

### 5.2 `SMARTSTORE-R0-SELLER-ACCOUNT`

Required proof:

- real protected `SMARTSTORE_SELLER_ACCOUNT` GET using current committed session;
- HTTP/JSON/success predicate evaluated;
- non-empty `accountUid` observed;
- expected vs observed identity comparison performed;
- evidence bound to current credential/session generation;
- no weak field overrides `accountUid` mismatch.

### 5.3 `SMARTSTORE-R0-TOKEN-REISSUE-WINDOW` — separate long-horizon session

For the main M2 acceptance campaign:

```text
status = DEFERRED_LONG_HORIZON
required_for_m2_acceptance = false
```

This slot is intentionally removed from the main M2 critical path. The observation requires real elapsed time and has high recovery cost: a failed `<30m` observation may require issuing a new token and waiting through another long token-lifetime cycle before the same boundary can be observed again.

It therefore runs only under a **separately reviewed long-horizon session** with its own request budget/evidence record. It does not consume or extend the main M2 campaign budget in §6.

When that separate session runs, it must observe both sides of the provider's documented remaining-lifetime window using real elapsed time based on the initially observed `expires_in`.

Required observations:

1. an early token request while the current token has **more than 30 minutes remaining**;
2. a later token request only after the current token has **less than 30 minutes remaining**;
3. the exact returned behavior for each request (same-token semantics, new-token semantics, rejection, or other trustworthy provider result) recorded without exposing token values;
4. after the late observation, protected seller-account access with the current committed token;
5. one protected seller-account read using the pre-late-reissue token to measure whether overlap validity exists, **only if** a distinct newer token was observed. If no distinct token was returned, record `NOT_APPLICABLE_SAME_TOKEN` rather than inventing overlap evidence.

The wait is determined from actual `expires_in`; with the current documented ~180-minute base lifetime this may require roughly 150 minutes before entering the `<30m` observation window.

PASS means the required observations were made within the separate session's reviewed budget with trustworthy timestamps/evidence.

If measured provider behavior differs from current NAVER documentation, mark the slot `MEASURED_CONTRACT_REVIEW_REQUIRED`; do not fail merely because the provider behaved differently from the hypothesis.

Deferral does not mean the observation is unnecessary. `AUTH.md` full-contract `verified_at` remains blocked until this long-horizon requirement and its persistence-policy review are satisfied.

### 5.4 `SMARTSTORE-R0-FIRST-TOKEN-CRASH`

This is the final real-provider experiment in the **main M2 campaign**.

Preconditions:

- all Layer 1 invariant tests green;
- A0 accepted;
- normal token/account proof accepted;
- restart proof accepted;
- regression floor green before starting;
- fresh acceptance data directory with no committed SmartStore session.

The reissue-window slot is **not** a precondition because it belongs to the separate long-horizon session in §5.3.

Experiment:

1. obtain a successful real token response;
2. deterministically terminate/fault-inject after full remote response and before durable local session commit;
3. restart from the same local data directory;
4. record the bounded recovery behavior;
5. perform only the recovery token issuance allowed by the hard budget;
6. after a session is durably committed, perform a fresh seller-account identity proof.

**Crash-attempt sub-budget:** at most **2 token-issuance attempts total** may be used to exercise the crash boundary: the initial attempt plus at most one retry if the harness/injection fails to hit the required post-response/pre-commit boundary.

Unused global token capacity in §6 MUST NOT be repurposed for an extra crash attempt. If the second crash-boundary attempt still does not exercise the required boundary, the crash-attempt sub-budget is exhausted and the main campaign becomes:

```text
campaign_outcome = BUDGET_EXHAUSTED
M2 acceptance = NOT_ACCEPTED
```

A new crash attempt requires a new reviewed campaign/budget extension and a fresh evidence record.

**PASS criterion:** the crash boundary was actually exercised and the post-crash provider/local behavior was measured and recorded safely.

PASS does **not** require a predetermined NAVER recovery behavior.

Whether NAVER permits immediate reissuance, returns equivalent authorization material, rejects the request, or exhibits another trustworthy result is observation data. A result contradicting the frozen auth assumptions triggers contract review; ICBM must not invent a guarantee.

Implementation defects remain FAIL, including committing the candidate before the injected crash point, fabricating READY without commit+identity proof, exceeding either request budget, or leaking bearer material.

### 5.5 `SMARTSTORE-R0-APP-REAUTH`

For M2 acceptance:

```text
status = BLOCKED_BY_TIME
required_for_m2_acceptance = false
```

The real application-reauth condition cannot reasonably be manufactured merely to close the milestone.

M2 must not infer it from application age, generic `401`, generic `GW.AUTHN`, or token failure.

If/when a trustworthy real condition or provider-supported machine-visible equivalent becomes observable later, this slot can be measured under a separate reviewed plan and may then unlock durable automatic `APPLICATION_REAUTH_REQUIRED` mapping.

## 6. Hard real-account request budget

The **main M2 acceptance campaign** has a hard SmartStore budget of:

| Endpoint / request kind | Hard cap | Purpose |
| --- | ---: | --- |
| `POST SMARTSTORE_AUTH_TOKEN` | **8** | normal issuance, bounded recovery/contingency, crash-boundary attempts, post-crash recovery |
| `GET SMARTSTORE_SELLER_ACCOUNT` | **6** | baseline identity proof, restart proof, post-crash proof, bounded read contingency |
| Any other SmartStore endpoint | **0** | M2 allow-list forbids all other calls |
| Product/category/image endpoint calls | **0** | all remain NOT_ADOPTED |
| A0 permission-attestation handling | **0** | local/operator evidence only |

These are independent hard caps, not a combined pool. A token call cannot borrow from unused seller-account capacity and vice versa.

The acceptance harness MUST count requests centrally by endpoint ID **before transport send**.

If sending the next request would exceed its endpoint cap, the request is not sent and the campaign becomes:

```text
campaign_outcome = BUDGET_EXHAUSTED
M2 acceptance = NOT_ACCEPTED
```

No overrun is permitted. No exploratory calls are permitted. A new campaign or budget extension requires explicit reviewed approval and a fresh evidence record.

### 6.1 Main-campaign planned sequence

```text
T1   baseline token issuance
A1   baseline seller-account identity proof
A2   restart seller-account proof using the committed token
     regression recheck
T4a  fresh-data-dir token issuance + injected crash before local commit
T4b  optional single crash-boundary retry only if T4a did not hit the required boundary
T5   bounded post-crash recovery token issuance after a successful crash-boundary exercise
A3   fresh seller-account identity proof after committed recovery
     final regression + evidence closeout
```

`T = token POST`, `A = seller-account GET`.

The labels retain T4/T5 terminology from the original design for audit continuity; they are not an instruction to manufacture unused T2/T3 calls in the main campaign.

Worst-case planned main-path usage before generic contingency is therefore:

```text
POST SMARTSTORE_AUTH_TOKEN = 4
GET  SMARTSTORE_SELLER_ACCOUNT = 3
```

The remaining headroom under the 8/6 caps is reserved only for **bounded recovery of an already-planned operation under the owning retry/error contract**:

```text
Token contingency reserve  = 4 calls maximum
Seller-read contingency    = 3 calls maximum
```

That reserve may repeat an already-planned token or seller-account operation only after a retryable/diagnostic condition permitted by the frozen contracts. It MUST NOT create a new measurement objective, probe a new endpoint, add a third crash-boundary attempt, or be borrowed by the separate reissue-window session.

The gap between planned calls and the hard caps is deliberate contingency for bounded recoverable failures. Contingency is not permission for exploration, extra crash attempts, or new endpoint probes.

### 6.2 Separate long-horizon session

`SMARTSTORE-R0-TOKEN-REISSUE-WINDOW` does **not** run inside the main M2 campaign above.

Its separately reviewed session will define its own hard budget before any provider call is sent. That budget must cover:

```text
>30m reissue observation
real elapsed time
<30m reissue observation
current-token seller-account proof
one immediate old-token overlap read only if a distinct newer token exists
```

If the provider returns the same token/material such that overlap cannot be meaningfully distinguished, record `NOT_APPLICABLE_SAME_TOKEN`; do not spend an extra call trying to manufacture overlap evidence.

## 7. Evidence artifact contract

The final acceptance record must make each slot independently auditable.

Required top-level provenance block:

```text
Acceptance evidence commit:   <sha>
Runtime code last changed at: <sha>
<runtime>..<evidence>:        <expected docs/evidence-only delta>
<evidence>..HEAD:             <closeout-only delta, if any>
```

Each slot must have one evidence row:

| Field | Required value |
| --- | --- |
| `evidence_id` | stable R0/A0 slot ID |
| `evidence_kind` | `PROVIDER_MEASURED` or `OPERATOR_ATTESTED` |
| `status` | `PASS`, `MEASURED_CONTRACT_REVIEW_REQUIRED`, `DEFERRED_LONG_HORIZON`, `BLOCKED_BY_TIME`, or `FAIL` as applicable |
| `required_for_m2_acceptance` | boolean |
| `observed_at` | timestamp/range |
| `application_fingerprint` | non-reversible fingerprint where applicable |
| `credential_generation` | where applicable |
| `session_generation` | where applicable |
| `endpoint_ids` | exact adopted endpoint IDs used; empty for A0 |
| `request_count` | per endpoint |
| `evidence_ref` | repository-controlled sanitized evidence artifact/section |
| `result_summary` | bounded, no secrets/tokens/PII |
| `contract_impact` | `NONE` or explicit review reference |

Campaign-level closeout must also record:

- endpoint hard caps;
- actual request counts;
- crash-attempt sub-budget usage;
- whether any request was blocked before send by the budget gate;
- `campaign_outcome`, including `BUDGET_EXHAUSTED` when applicable.

Do not use a single "R0 complete" flag.

The final report must separately summarize:

```text
Required R0: 3/3
A0:          1/1
Long-horizon R0:
  TOKEN-REISSUE-WINDOW = DEFERRED_LONG_HORIZON (non-gating) or accepted result
  APP-REAUTH           = BLOCKED_BY_TIME (non-gating) or accepted result
Contract reviews opened from measurements: <n>
```

This prevents operator attestation from being laundered into provider-measured runtime truth and prevents deferred long-horizon work from being misreported as completed.

## 8. Layer 4 — regression floor

M2 cannot pass by breaking previously accepted foundations.

Required floor:

- current required CI jobs all green;
- M0 acceptance remains **24/24 PASS** from a clean checkout/runtime;
- M1 KM통상 CONNECT remains accepted and its relevant regression tests stay green;
- Issue #4 / ADR-0006 single-data-directory ownership remains enforced;
- one-worker/write-coordinator assumptions remain intact;
- no product collection/registration side effect is introduced by M2 CONNECT;
- zero NOT_ADOPTED SmartStore calls in acceptance evidence.

Any regression in these floors is M2 FAIL regardless of SmartStore happy-path success.

## 9. Execution order

The main M2 acceptance execution order is frozen to minimize irreversible/expensive provider experiments.

```text
A. static/unit/mock contract invariants
B. A0 permission-attestation handling (0 provider calls)
C. normal real token + seller-account proof
D. restart proof
E. regression recheck
F. FIRST-TOKEN-CRASH experiment last among provider experiments
G. final regression + secret/evidence scan + report closeout
```

`SMARTSTORE-R0-FIRST-TOKEN-CRASH` is intentionally last because it creates the least-reversible provider/local uncertainty and its recovery behavior is itself the measurement target.

`SMARTSTORE-R0-TOKEN-REISSUE-WINDOW` is not inserted before FIRST-TOKEN-CRASH. It belongs to a separate long-horizon observation session because the real elapsed-time wait and failure-recovery cost are incompatible with the main acceptance critical path.

`SMARTSTORE-R0-APP-REAUTH` remains a separate later observation while `BLOCKED_BY_TIME`.

## 10. PASS / FAIL / REVIEW semantics

### PASS

Use PASS when the acceptance condition itself is proven.

For an observational R0 slot, PASS means the required provider behavior was measured safely; it does not mean the provider matched ICBM's prior expectation.

### `MEASURED_CONTRACT_REVIEW_REQUIRED`

Use this when:

- the measurement is trustworthy and within budget;
- provider behavior materially contradicts the current adopted/documented contract;
- implementation itself followed the frozen request/safety rules.

This state closes the measurement task but opens contract review. M2 final acceptance is blocked only if the contradiction affects a safety/READY invariant required for CONNECT and remains unresolved.

### `DEFERRED_LONG_HORIZON`

Used for `SMARTSTORE-R0-TOKEN-REISSUE-WINDOW` when the separate elapsed-time observation session has not yet run.

It is explicitly non-gating for M2, but it does not satisfy AUTH full-contract verification.

### `BLOCKED_BY_TIME`

Used for `SMARTSTORE-R0-APP-REAUTH` while the real/provider-supported application re-auth condition is not practically observable.

It is explicitly non-gating for M2.

### `BUDGET_EXHAUSTED`

This is a campaign outcome, not a successful evidence status.

Use it when an endpoint hard cap or the frozen crash-attempt sub-budget prevents the next required request/attempt. The blocked request is not sent and M2 remains `NOT_ACCEPTED` for that campaign.

Unused capacity elsewhere cannot be reallocated without reviewed approval.

### FAIL

Examples:

- wrong request shape/method/path;
- unadopted endpoint call;
- request budget exceeded or bypassed;
- secret/token leakage;
- READY without required durable commit/current identity proof;
- A0 path performs provider network I/O;
- A0 evidence is rendered/treated as machine-verified;
- fingerprint/mapping/freshness invalidation fails;
- injected crash boundary was not actually reached within its frozen sub-budget;
- evidence cannot prove which endpoint/generation produced the result;
- prior accepted M0/M1 ownership/regression floor breaks.

## 11. Final expected M2 truth

A successful M2 CONNECT acceptance may end with:

```text
auth               = READY
write_scope        = READY | MISSING | UNKNOWN
write              = UNVERIFIED
contract_freshness = CURRENT
```

and, independently:

```text
SMARTSTORE-R0-TOKEN-REISSUE-WINDOW = DEFERRED_LONG_HORIZON
SMARTSTORE-R0-APP-REAUTH           = BLOCKED_BY_TIME
APPLICATION_REAUTH_REQUIRED automatic detection = DISABLED
AUTH.md verified_at = null
```

`PERMISSIONS_SCOPES.md verified_at` may also remain `null` after A0 acceptance because `NO_MACHINE_READABLE_PERMISSION_SOURCE` is a valid structural limitation, not an unfinished A0 task.

A healthy operator-attested permission example remains:

```text
인증      ● 연결됨
등록 권한 ◐ 권한 확인됨 (관리자 화면 확인)
실제 등록 ○ 미확인
```

No layer becomes greener by borrowing evidence from another layer.
