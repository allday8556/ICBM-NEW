## 1. What M5 will claim

For one accepted canonical product, the REGISTER segment works end to end and cannot create a second listing:

```text
SmartStore CONNECT usable
→ Draft / preflight READY
→ marketplace publication assets prepared (when CREATE needs provider image identities)
→ immutable RegistrationSnapshot per provider-listing unit
→ one authorized CREATE per RegistrationIntent
→ if needed, deterministic reconcile
→ marketplace read-back
→ exact critical-field comparison against the Snapshot: PASS
→ MarketplaceRegistration(+Item) saved against the same canonical Product/Item(s)
→ restart
→ read-back / reconcile remains stable
→ repeating the same Intent cannot create a second listing
```

## 2. Bounded scope

M5 acceptance will **not** claim:
- **M6 OPERATE.** No recurring listing status, price, stock, order, inquiry or claim ingest, and no recurring detection of external deletion (ADR-0014 §23).
- **UPDATE or DELETE.** No marketplace update, repair, deactivate or delete operation. Any cleanup is a separate protected write with its own authorization (ADR-0014 §24).
- **Bulk registration.** One canary product first; bulk registration is later work.
- **AI.** Registration works with no AI provider configured (ADR-0014 §18).
- **Image Studio or Detail Guidance.** Only the M4 derived-image owner transforms binaries; the detail composition may be body-only (ADR-0014 §5, §19).
- **A second marketplace or supplier.** The first vertical closes first (ROADMAP §12).

M5 acceptance by itself does not close the first vertical. M6 and M6.5 follow.

## 3. How acceptance will proceed

The stages follow Issue #89 §20. Each needs its own authorization.

1. **Offline and fake first.** The M5 acceptance harness (PR-F) runs by default with no provider capability: fake transports, `DRY_RUN`, CI provider-zero. It proves the contract offline:
   - idempotent Intent resolution across restart and concurrent sends;
   - no blind CREATE resend after an UNKNOWN, and the conflict-scope block for a new Snapshot (ADR-0014 §10);
   - the non-overlapping-group twin;
   - the `SINGLE_LISTING_WITH_OPTIONS` subset mismatch, with no CREATE for missing Items (§11);
   - `SEPARATE_LISTINGS` per-listing partial success, and a derived `PARTIAL` (§12);
   - external removal: assertion alone changes nothing, proven absence keeps history and allows a fresh preflight with a new Snapshot and Intent (§14);
   - read-back compared to the immutable Snapshot (§11);
   - sanitation before any raw evidence is hashed (§15).
2. **Then a separately user-authorized single SmartStore canary.** Only after the implementation PRs are audited and merged, exact main is green, the endpoints are adopted, and the user explicitly authorizes a bounded write scope:
   - **the necessary image upload is part of that protected write scope**;
   - one canary product, one provider-listing unit;
   - CREATE → reconcile if needed → read-back comparison against the Snapshot;
   - restart and replay prove no duplicate listing.
3. **Exact-main closeout.** The final acceptance run executes on the exact merged main SHA after PR-F, and its evidence is recorded here. **M5 becomes ACCEPTED only when the architect accepts that record.**

## 4. Required evidence (Issue #89 §19)

- no duplicate listing from replay or restart;
- an ambiguous CREATE outcome cannot be blindly resent;
- registration Item correspondence survives provider option ordering and normalization (`registration_item_key`);
- the Snapshot stays immutable after later current-state changes;
- provider product and item identities read back and map to the same canonical Product and Items;
- no supplier hotlink is published;
- source, product, pricing and image history is unchanged;
- no M6 recurring operational ingest is claimed;
- only sanitized provider evidence is retained;
- `product_registration.write` becomes `READY` only through the conditions of ADR-0014 §16.
