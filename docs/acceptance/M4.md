## 1. What M4 claims

Accepted COLLECT source truth traverses the M4 production owners end to end, on a fresh dedicated data root:

```text
ProductFactsRevision / SourceAsset
→ current source revision
→ ProductGroup (the canonical Product) and its membership
→ ListingComposition / Item
→ BASE_PRODUCT or SOURCE_OFFER binding
→ PricingSnapshot per Item and pricing context
→ derived image lineage, operator image selection, exact-binary QA
→ base and pricing readiness (derived, never stored)
→ durable read-back
→ process restart
→ source revision change
→ correct staleness and explicit refresh
```

## 2. Bounded scope

M4 does **not** claim:
- **Source SKUs.** Positive option-axis or configuration SourceSKU materialization, and SKU-specific tier mapping. Only product-level quantity offers exist (ruling 5738760913).
- **Composed fulfillment.**
- **Grouping.** Cross-supplier grouping, MERGE or SPLIT. Consequently no M4 rule produces `DUPLICATE`, and the harness reports it as `NOT_EXERCISED`. Its place in the precedence is pinned by a unit test.
- **M5 work.**
  - Any marketplace listing, option, category, notice or preflight.
  - Any registration candidate. `RegisterService.registration_candidate_count()` stays 0.
- **Provider work.** Any supplier, marketplace, AI or OCR call. The harness has no such capability.
- **Quantity resale guidance.** Quantity-scoped resale-price guidance (5738886070).

## 3. The harness

```text
python scripts/m4_acceptance.py --root <fresh-dedicated-root>
python scripts/m4_acceptance.py --verify <root>/m4-acceptance-report.json
```

**Exit status:**
- 0: the report has no problem;
- 1: a check failed, or a report does not verify;
- 2: the root was refused.

No approval phrase exists, because the run has no provider capability.

### 3.1 The root (`scripts/m4accept/root.py`)

A root is accepted only when every one of these holds:
- **No preserved campaign.** No path component names a preserved campaign runtime (`m3-recon-*`, `m3-accept-*`, in any case or separator). This is judged on the path as given, before anything is created or listed, and again once resolved.
- **Dedicated.** The root lies outside the repository and outside the default and configured ICBM data directories.
- **Fresh.** It is new, empty, or holds only the harness marker in state `INITIALIZED`.

A root that ran once is never reused. Only the root itself is ever listed; no sibling directory is enumerated. Application data lives under `<root>/data`. The marker `m4-acceptance-root.json` ends `PASSED` or `FAILED`.

### 3.2 Offline guards (`scripts/m4accept/guards.py`)

Each guard is armed for the run only, and every count is measured:
- **Network.** The process egress audit hook counts every blocked non-loopback attempt. No supplier egress grant may open.
- **Imports.** A meta-path guard refuses AI, OCR, marketplace, SmartStore and supplier CONNECT services, supplier transports, the KM collection, browser automation, HTTP clients and the collection job. Each attempt is counted, and the kinds of module loaded during the run are listed. ORM table modules are not provider paths; the schema aggregate loads them.
- **Paths.** A file-open, listing and database audit hook refuses and counts any path naming a preserved campaign. It counts every write outside the root, bytecode caches aside.

The four provider counters (supplier writes, marketplace reads/writes, AI calls, OCR calls) are reported as 0 only when every guard held. Otherwise they are reported as unknown, never as an invented 0.

### 3.3 Composition (`scripts/m4accept/owners.py`)

The run composes exactly the production classes `app.container` wires, over the same database, clock, audit log and data-root directories:
- the M4 owners: materializer, products, pricing, images and readiness;
- COLLECT's run, revision and source-asset stores.

No CONNECT service, supplier gateway, collection transport, SmartStore caller, job worker or secret store exists in the run. The data root is owned as the application owns it (ADR-0006): the lease comes first, and it is released only after the database is disposed.

### 3.4 Synthetic source truth (`scripts/m4accept/synthetic.py`)

Every input is invented: the supplier key `m4-synthetic`, the product identities, names, amounts and PNG bytes. The source truth is written only through COLLECT's own stores:
- the source-asset store keeps the bytes;
- the collection-run store opens a run and settles it RECORDED;
- the revision store validates and appends the revision.

No raw row is inserted, and no M4 truth is written by SQL. The only SQL is read-only (`mode=ro`) evidence.

## 4. Scenarios

The pricing context is invented: `m4_market`, no account, fee rate 10%, other costs 0, `CEIL_KRW_1`, policy v1 (35% target, 10% minimum).

**S1 BASE_PRODUCT.**

| step | expected |
|---|---|
| R1: price 10,000, FIXED shipping 2,500, minimum 18,000, options/tiers ABSENT, ON_SALE, two CONFIRMED images | one ProductGroup, one CONFIRMED member (membership revision 1), the default single-unit Item, a BASE_PRODUCT binding on R1 |
| pricing R1 | target 22,728 is **above** the minimum. Final **18,000 = the minimum**, basis `MINIMUM_SALE_PRICE`, fee 1,800, profit 3,700, margin 2,055 bp, guard OK |
| images R1 | a completed derivation of the representative image, stored apart from source assets. An operator selection (derived representative + source detail): readiness first names the missing selection, then the missing QA. PASS QA for both exact binaries: base and pricing READY |
| restart | every identity, pointer and readiness fingerprint reads back identically, with no row or byte written. Materialization and pricing replays are UNCHANGED |
| R2: price 11,000 | same source product, group and Item; R1 unchanged; the binding closed and replaced; the old snapshot kept. Pricing STALE (`PRICING_SNAPSHOT_SUPERSEDED`); images STALE (`IMAGE_SELECTION_STALE`, `IMAGE_DERIVATION_STALE`) |
| refresh R2 | repriced: final 18,000, profit 2,700. A new derivation of the same artifact; RESELECTED; QA under R2. READY again, and no history rewritten |

**S2 QuantityOffer.** Generic prices are 11,111 and 33,333, which equal no tier total, multiple or quotient.

| step | expected |
|---|---|
| Q1: tiers 1 = 19,900, 2 = 37,900, 3 = 53,900; FREE shipping; no minimum | three exact offers, no SourceSKU; three Items (q1 = the default signature); exact SOURCE_OFFER bindings with fulfillment 1/2/3 |
| pricing Q1 | costs 19,900 / 37,900 / 53,900 → finals 36,184 / 68,910 / 98,000, all TARGET_MARGIN/OK |
| images Q1 | every Item starts REVIEW_REQUIRED (`IMAGE_SELECTION_MISSING`). q1's selection is not inherited by q2/q3. One selection per Item, QA per exact binary: READY |
| Q2: tiers 2 = 36,900, 3 = 52,900 | same Items; three new revision-scoped offers, Q1's kept; bindings replaced. Pricing and images STALE, then repriced (36,184 / 67,093 / 96,184), reselected and READY |

**S3 BLOCKED.**

| step | expected |
|---|---|
| SOLD_OUT, price 10,000, FIXED 2,500, minimum 11,000 | base BLOCKED (`SOURCE_STOCK_SOLD_OUT`). Final 11,000 = the minimum, guard LOSS with both guard reasons: pricing BLOCKED |

**Final restart.** The full read-back of all three products and five Items matches durable state. No row or byte is written, and every replay is UNCHANGED. Every row and stored byte that S1 made durable before its first restart is still identical; only an open binding may have closed its window.

## 5. The report

`<root>/m4-acceptance-report.json` (schema `icbm-m4-acceptance-report/v1`) holds:
- the run id, code SHA and alembic head;
- the scenario identities and exact amounts;
- the restart proofs;
- the readiness examples (`READY`, `REVIEW_REQUIRED`, `STALE`, `BLOCKED`; `DUPLICATE` `NOT_EXERCISED`);
- the hard-zero evidence and the preserved-campaign access count;
- every check with its result;
- `problems[]`;
- `report_digest`, SHA-256 over the canonical JSON of everything else.

**Sanitizing.** Before the report is written, it is scanned for:
- URLs and absolute or backslash paths;
- the run's own paths;
- secret-like words and the approval-phrase keyword;
- non-ASCII business text.

A leaking report is withheld and replaced by its problems.

## 6. Evidence and closeout

- **PR-head rehearsal.** The PR-F evidence comment in Issue #80 records it: the exact PR head, a fresh root outside the repository and every data directory, and the report digest. It shows only that the harness and the implementation agree.
- **Final acceptance.** It is pending until PR-F is audited, cross-audited, approved and merged. Then the harness runs once more, on the exact merged main SHA and a new root. That report's SHA, digest and check counts are recorded here, and M4 becomes ACCEPTED only when the architect accepts that record.
