## 1. What M5 will claim

For one accepted canonical product, the REGISTER segment works end to end and cannot create a second listing:

```text
SmartStore CONNECT usable
→ Draft / preflight READY
→ marketplace publication assets prepared (when CREATE needs provider image identities)
→ immutable RegistrationSnapshot per provider-listing unit
→ one authorized CREATE per RegistrationIntent
→ if needed, deterministic reconcile
→ marketplace read-back
→ exact critical-field comparison against the Snapshot: PASS
→ MarketplaceRegistration(+Item) saved against the same canonical Product/Item(s)
→ restart
→ read-back / reconcile remains stable
→ repeating the same Intent cannot create a second listing
```

## 2. Bounded scope

M5 acceptance will **not** claim:
- **M6 OPERATE.** No recurring listing status, price, stock, order, inquiry or claim ingest, and no recurring detection of external deletion (ADR-0014 §23).
- **UPDATE or DELETE.** No marketplace update, repair, deactivate or delete operation. Any cleanup is a separate protected write with its own authorization (ADR-0014 §24).
- **Bulk registration.** One canary product first; bulk registration is later work.
- **AI.** Registration works with no AI provider configured (ADR-0014 §18).
- **Image Studio or Detail Guidance.** Only the M4 derived-image owner transforms binaries; the detail composition may be body-only (ADR-0014 §5, §19).
- **A second marketplace or supplier.** The first vertical closes first (ROADMAP §12).

M5 acceptance by itself does not close the first vertical. M6 and M6.5 follow.

## 3. How acceptance will proceed

The stages follow Issue #89 §20. Each needs its own authorization.

1. **Offline and fake first.** The M5 acceptance harness (PR-F) runs by default with no provider capability: fake transports, `DRY_RUN`, CI provider-zero. It proves the contract offline:
   - idempotent Intent resolution across restart and concurrent sends;
   - no blind CREATE resend after an UNKNOWN, and the conflict-scope block for a new Snapshot (ADR-0014 §10);
   - the non-overlapping-group twin;
   - the `SINGLE_LISTING_WITH_OPTIONS` subset mismatch, with no CREATE for missing Items (§11);
   - `SEPARATE_LISTINGS` per-listing partial success, and a derived `PARTIAL` (§12);
   - external removal: assertion alone changes nothing, proven absence keeps history and allows a fresh preflight with a new Snapshot and Intent (§14);
   - read-back compared to the immutable Snapshot (§11);
   - sanitation before any raw evidence is hashed (§15);
   - a `BLOCKED`, `DUPLICATE`, `STALE` or `REVIEW_REQUIRED` non-asset candidate never reaches a marketplace asset upload, and a dependency change between the candidate and the final preflight allows no CREATE (§3);
   - an operator assertion never turns an UNKNOWN into `NOT_APPLIED_PROVEN` or releases its conflict scope (§10);
   - every durable payload and request digest is computed from the sanitized representation (§15).
2. **Then a separately user-authorized single SmartStore canary.** Only after the implementation PRs are audited and merged, exact main is green, the endpoints are adopted, and the user explicitly authorizes a bounded write scope:
   - **the necessary image upload is part of that protected write scope**;
   - one canary product, one provider-listing unit;
   - CREATE → reconcile if needed → read-back comparison against the Snapshot;
   - restart and replay prove no duplicate listing.
3. **Exact-main closeout.** The final acceptance run executes on the exact merged main SHA after PR-F, and its evidence is recorded here. **M5 becomes ACCEPTED only when the architect accepts that record.**

## 4. Required evidence (Issue #89 §19)

## 5. The offline harness (PR-F §A)

```text
python automation/acceptance/m5/m5_acceptance.py --root <fresh-dedicated-root>
python automation/acceptance/m5/m5_acceptance.py --verify <root>/m5-acceptance-report.json
```

`--root` names a new or empty directory dedicated to one run, outside the repository and every
ICBM data directory, and never a preserved campaign runtime. The code must be an exact clean
checkout: a tracked change, an untracked file or an ignored source refuses the run before anything
is created. Run data lives only under `<root>/data`; the sanitized report is written to
`<root>/m5-acceptance-report.json`. Exit 0 means every check passed, 1 that the report holds a
problem, 2 that the root or the checkout was refused.

**The report** (`icbm-m5-acceptance-report/v1`) carries the exact git SHA and checkout counters,
the Alembic head, the execution mode, the execution policy version, the endpoint-adoption
snapshot, the account scope, each scenario's evidence, every check with its observation, the
measured guard counters, the derived canary readiness and a SHA-256 digest over all of it that
`--verify` recomputes. It holds no credential, session, signed URL, approval text, absolute path
or raw provider payload: a report that would leak any of those is withheld and says so.

**What the run proves offline.** The seventeen acceptance-plan cases of §3, driven through the real
production owners: the registration store and its triggers, the preflight and Snapshot builder,
the execution owner over the M0 job system, the execution-scope brake, and the M4 product, pricing
and image owners that feed them. Case 18 adds the durable preparation owner (§27): authored, read
back after a restart, evaluated with no job in existence, frozen with its provenance recorded, and
edited into a new revision that leaves the frozen Snapshot exactly as it was.

**What it declares instead of proving, and why each one is a declaration.** The report names a
reason for every seam, because the gaps are not the same gap:

**Provider-zero.** The guards refuse every HTTP client, browser, AI, OCR and supplier transport

## 7. The Registration Management surface (PR-F §B)

The screen is built **per provider-listing unit**, never per Draft (ADR-0014 §2, R3). A
`SEPARATE_LISTINGS` Draft with two Items is two units, each with its own Snapshot, Intent, Attempt
history, conflict scope and actions; a frozen unit's Items and `registration_item_key`s come only
from that Snapshot's own `ItemSnapshot` rows, and the Items a shape would still form appear
separately as preparations. The canary's single-unit gate counts these units.

Each unit carries, from the owner that holds it:

| shown | owner |
| --- | --- |
| listing shape, account, binding, Draft revision, Snapshot identity and fingerprint | the registration store |
| category, its mapping and taxonomy revisions, and each required attribute / notice field with whether the Snapshot's frozen payload provides it | the Snapshot payload and the reviewed category metadata |
| each Item's **pinned** price and basis, the **current** M4 price for the account's target context, and whether the pin is still current | the M4 pricing owner, through the preflight owner's gathering |
| each Item's M4 base and pricing readiness with **every** reason code | the M4 readiness owner |
| the selected publication assets as exact identities with their QA verdict | the M4 image owner (current selection) or the frozen payload (frozen unit) |
| the preflight status with every reason code, and whether its fingerprint still matches the Snapshot | the preflight owner, re-evaluated from current truth |
| Intent state, Attempts, read-back/verification, execution-scope brake, marketplace identity once proven | the registration store and the execution owner |

**The authoring path (ADR-0014 §27, architect decision `5751540323`).** A preflight is derived from
the operator's own inputs — the category selection, the listing values and the detail composition —
and PR-F reported that no durable owner held them. The architect selected option (a) and authorized
**migration 0018**, so those inputs now have one:

- `POST /api/v1/register/preparations` records what an operator authored for one provider-listing
  unit; `POST /api/v1/register/preparations/{id}` appends the next revision, and an earlier one is
  never edited in place;
- `GET /api/v1/register/preparations/{id}` reads it back — after a reload and after a restart;
- `POST …/evaluate` asks the preflight owner what those inputs are worth against current truth,
  with every reason code, and **needs no job**;
- `POST …/freeze` freezes the Snapshot and opens its Intent through the owners that already decide
  READY and freshness; the Snapshot records which exact authored revision and fingerprint produced
  it.

The preparation stores **inputs only** — no readiness, no status, no reason code, no price, image,
capability or provider fact — and the `register.create` job payload stays a frozen **execution**
copy of a revision, never the authoring truth. A unit with neither a preparation nor a job still
says so, with `preflight_unavailable_reason = REGISTER_PREFLIGHT_INPUTS_NOT_DURABLE`, rather than
showing a status it cannot stand behind. M4 truth — price, base and pricing readiness, images and
QA — is shown for **every** unit, frozen or not, because those owners hold it.

The provider duplicate lookup remains `NOT_ADOPTED`. IMAGE UPLOAD adoption alone does not authorize
LIVE execution, a real upload, CREATE, a canary, or M5 acceptance.

### 9.1 The provider-evidence verdict: `INSUFFICIENT`

The architect's review of the official provider contract for CREATE and for a deterministic
reconcile lookup closed **`INSUFFICIENT`** (Issue #89 `5768247290` → `5768312853` → `5768347233`;
ADR-0014 §17.2). The confirmed blockers:

- no official CREATE idempotency or ambiguous-outcome replay-safety guarantee;
- a seller-code search may return similar, partial or exact matches;
- no official uniqueness guarantee for `sellerManagementCode`;
- no official freshness or read-after-write guarantee that would make a zero-result lookup an
  authoritative absence.

The deterministic seller-side listing identity is ICBM's own correlation identity (ADR-0014 §7),
never a provider uniqueness proof: an empty lookup result is not proven absence, and an operator
assertion is never the evidence. So `SMARTSTORE_PRODUCT_CREATE_V2` and `SMARTSTORE_PRODUCT_SEARCH`
stay `NOT_ADOPTED`, `product_registration.write` stays `UNVERIFIED`, execution stays `DRY_RUN`, and
the canary stays `BLOCKED`. *(Amendment note: `SMARTSTORE_PRODUCT_CREATE_V2` was later adopted by
its own separately authorized slice — §6 above and ADR-0014 §17.3. **The verdict recorded here is
unchanged and was not the adoption condition** (ADR-0014 §17.2, ADR-0018 §6.1); adoption overturned
nothing, `SMARTSTORE_PRODUCT_SEARCH` is unchanged, and `product_registration.write`, the execution
mode and the canary are all unchanged.)*

Gate 3 area 4 re-reviewed the official evidence and confirmed the verdict (`5844652548` →
`5844770185`). The seller management code is officially non-unique, and a CREATE whose response never
arrived is officially not proof of non-application. **The verdict stands, but overturning it is no
longer what reopens the canary.**

Under the revised strategy (ADR-0014 §28, ADR-0018 §6.1, architect decision `5845062336`) — never
resend while the outcome is unknown, positive-only reconcile, and durable ambiguity isolation — the
canary can leave `BLOCKED` only when all of these hold:
- CREATE and the positive-only reconcile contract are each separately adopted — **both adopted**,
  CREATE by its own slice (ADR-0020 §4 order 1) and the positive-only reconcile contract by its own
  slice (order 2; ADR-0014 §17.4);
- no `UNKNOWN` CREATE is ever resent — enforced, and pinned by the adoption slice's own tests;
- every Gate-3 readiness prerequisite holds — **none of the missing ones is closed**;
- an explicit user and architect acceptance of the residual risk is recorded — **not recorded**.

A zero-result lookup stays non-authoritative: it never proves absence. Two of these hold — CREATE and
the positive-only reconcile path are adopted (the first condition) and the never-resend rule is
enforced — and neither lets the canary leave `BLOCKED`: every missing Gate-3 readiness prerequisite
and the residual-risk acceptance are still missing.
