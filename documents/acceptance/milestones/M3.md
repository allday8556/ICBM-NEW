## 1. What this milestone claims

```text
operator one-product URL
→ durable collect.product job
→ policed collection gateway (one product read)
→ supplier identity rule + field parser + image roles
→ bounded image fetches through the same gateway
→ generic SourceAssetRecorder (exact bytes, content-addressed)
→ generic ProductFactsRevisionStore.append
→ durable run result identity
→ DB row and API read-back agree
```

Ownership is fixed and is part of the claim: orchestration, the durable job, retry and error
mapping, correlation and result identity, source-asset persistence, revision persistence and the
read-back are **generic COLLECT core**. KM통상 contributes a profile, an identity rule, a field
parser and image-role rules, and owns no hashing, storage, revision, job or egress.

## 2. The capability boundary this milestone must not overstate

This section exists because two field capabilities are **not** evidence-backed yet. Final M3
acceptance must not claim them, and no document, release note or UI copy may imply them.

### 2.1 The retained evidence

The accepted Phase-A/B reconnaissance of `m3-recon-02` captured one KM통상 product twice. In both
captures that product states:

- **no options** — the page carries the platform's option container with a single hidden template
  row, and no `<select>` and no `<option>` at all;
- **no quantity tiers** — no tier table and none of the tier wordings (`수량별` appears zero
  times). The `quantity_price` span beside the order form is the cart line's own total for a
  quantity the reader has not chosen yet, not a supplier tier.

For that product those fields are therefore legitimately `ABSENT`. That is a reading of the page,
not a gap in the parser.

### 2.2 Option axes and configurations — CONFIRMED support is NOT accepted

Positive `CONFIRMED` support for **option axes and configurations** has **not** been
evidence-backed and has **not** been architect-accepted.

Current behaviour, and the only behaviour this milestone may claim: when option-looking evidence
appears, the parser records it as `REVIEW_REQUIRED`, keeping each axis and its values apart and in
the page's own source order in the evidence, and produces **no value**. No axis is named, no
configuration is composed, and nothing is inferred — no accepted evidence shows how this
storefront names an axis.

**Final M3 acceptance must not claim CONFIRMED option parsing capability.**

### 2.3 Quantity tiers — CONFIRMED support is NOT accepted

Positive `CONFIRMED` support for **quantity-tier values and source totals** has likewise **not**
been evidence-backed and **not** architect-accepted.

Current behaviour: tier-looking evidence stays `REVIEW_REQUIRED` with the page's own words kept,
and a source total is never divided into a unit price. No tier value is produced.

**Final M3 acceptance must not claim this capability.**

### 2.4 This limit is not a licence to guess

A missing capability is never a reason to fabricate a value or to widen a selector, a host or a
traversal. The way to add positive support is a separately reviewed evidence campaign and its own
PR — new bounded campaign, new campaign id, fresh operator approval. `m3-recon-02` is terminal and
is never replayed or edited.

## 6. Campaign `m3-accept-01` — prepared, NOT authorized

This section is kept as the historical record of how the campaign harness was specified.
`m3-accept-01` never collected anything for real. It was superseded (§6.6) and is kept unchanged.
Every later campaign ran this same harness, including the accepted `m3-accept-04` (§7).

The harness is `scripts/m3_accept.py` over `scripts/m3accept/`. It orchestrates and never collects:
every product read and image request goes through the production `ProductCollectionService`, the
production job runner and the policed gateways, and every asset and revision is written by generic
COLLECT core. A repository rule refuses the harness any import of the parser package, the asset
store or the revision store, and any call that parses, classifies or records.

**Nothing in this section authorizes a REAL request.** After the prep PR is audited and merged, the
exact `main` SHA is frozen, the manifest and target digest are reported, and only then does the
operator type `APPROVE <campaign id> <first 12 hex of that SHA> TWO-PASS-REAL`, which `approve`
shows and never generates. The campaign id is the one its ledger owns (§6.7).

### 6.1 Frozen per-pass and campaign ceilings

| Request class | per pass | campaign | note |
| --- | ---: | ---: | --- |
| `PRODUCT_READ` | 2 | 4 | normally 1; one job retry at most |
| `IMAGE_REQUEST` | 13 | 26 | the recon baseline is a maximum, never a target |
| `POLICY_READ` | 0 | 0 | |
| `CONNECT_CONTROL_READ` | 2 | 4 | the M1 owner's session proof, one per product attempt |
| `CONNECT_PROTECTED_READ` | 2 | 4 | the M1 owner's session proof, one per product attempt |
| `CONNECT_AUTHENTICATE` | 0 | 0 | a campaign never logs in and never recovers |
| AI / OCR / marketplace / supplier write | — | 0 | no transport exists; asserted at PREP and closeout |

Bytes: at most 2 MiB per image and 24 MiB of new image bytes per pass, both enforced by the
production path. 13 × 2 MiB is **not** a 26 MiB allowance. Same-product interval ≥ 60 s.

These are ceilings, not expected counts. A pass with no retry spends 1 control + 1 protected read;
a job retry brings that pass to at most 2 + 2; a third proof read is refused before send. The proof
reads are accounted for in one place only — `LedgeredConnectGateway`, immediately in front of the
production M1 owner's transport — so the ledger records the reads that were actually sent, and
nothing is reserved in advance of need.

Every request is reserved in the campaign ledger — committed durably — before it can be sent, and
only while its own pass runs. The ledger's triggers refuse a reservation over a per-pass or campaign
ceiling, refuse any change to the armed manifest or ceilings, and keep every table append-only. Job
retries reserve against the same ceilings.

### 6.2 States

```text
INITIALIZED → ARMED → APPROVED → PASS_A_RUNNING → WAITING_FOR_PACING → PASS_B_RUNNING
            → CLOSEOUT_READY → COMPLETED                  (HOLD and STOPPED are terminal)
```

`WAITING_FOR_PACING` is a state the operator leaves, not a loop: `run-pass --pass B` asks the
durable pacing store once, and if the product may not be read yet it returns the seconds remaining
with nothing reserved, nothing submitted and nothing sent. A `SameProductTooSoon` refusal costs no
request budget. A job retry inside a started pass belongs to the job owner; the pass reports
`IN_PROGRESS` and the next invocation resumes that same run.

### 6.3 Fresh session

A fresh session is a fresh application composition — its own ownership lease, database engine, job
runner and service graph — on the campaign's one dedicated data directory, loading the M1
connection owner that directory already holds. It is never a new supplier login. Each pass records
a session nonce, and PASS-B refuses the nonce PASS-A ran under.

### 6.4 Pass verdicts

A pass is judged from durable state alone: the run row, the revision as the read-back returns it,
and the ledger's own reservations and refusals.

| Observed | Verdict |
| --- | --- |
| run not `RECORDED`, or identity unresolved | `HOLD` (a campaign's own refusal: `STOPPED`) |
| a core field `REVIEW_REQUIRED` | `HOLD` |
| more product-evidence references than 13 | `HOLD` — reference 14 is never fetched, the ceiling is not raised |
| fewer than 13 | recorded as `SOURCE_DRIFT_UNDER_BASELINE`; `HOLD` if no confirmed representative or detail remains |
| exactly 13 | normal |
| an image refused at the 24 MiB pass total | `HOLD` — the safe incomplete revision is kept, the budget is not widened |
| any other unresolved image reference | `HOLD` |

A HOLD authorizes no second, wider run. Any budget change needs a new frozen campaign contract and
fresh approval.

Byte facts are recorded at arming from the retained phase-B findings only: the sampled sizes are
known, every other reference is unknown, and no request is made to find out. That 24 MiB suffices
for all 13 is **not** claimed.

### 6.5 The M1 connection (PR #71 review 5233744115)

**Session proof.** `ConnectService.collection_session` proves a stored session with one control
read and one protected read before it hands the session out — on every collection, a job retry
included. Those reads are budgeted as above. If the proof shows the stored session has lapsed and
the owner would log in, the ledgered gateway refuses the login before send and the pass stops; the
production owner records that as its own authentication failure, so the connection is left
unusable rather than recovered. There is no login or recovery budget.

**Where it lives.** The campaign runs on its own `<root>/data` only. An ordinary ICBM data
directory, or a path that resolves anywhere else, is not a substitute. The accepted M1 connection
must be established there by an ordinary CONNECT operation — outside `m3-accept-01`, before arming,
and not counted in its ledger. The harness never automates that login.

**The arm gate.** Arming refuses — before a manifest or a ceiling is persisted, so no approval can
exist — unless the M1 owner in `<root>/data` reports a locally usable connection and session. The
check composes the application with every transport refusing and reads the owner's own summary; it
never calls `collection_session` or `verify` and never sends a request. Each pass repeats the same
local check before it begins; live validity is the budgeted proof inside the pass.

### 6.6 run-pass: the armed target and the request log (Issue #52 ruling 5713773005)

**The armed target.** `run-pass --product-url` is a PREP gate. The URL is read through the same
`canonical_target` and `target_digest` arming used, and only the manifest's target digest passes: a
spelling the production transport reads as the armed URL passes, any other target is refused. The
gate runs with the other PREP gates, before the REAL environment, a fresh session, the pass state, a
reservation, a submission or a transport exists, and its refusal names digests, never the URL.
Closeout submits nothing and is given no target.

**The request log.** A standalone `run-pass` writes the application's own JSON log to
`<root>/data/logs/icbm.jsonl` with the existing `configure_logging`, under the data-directory lease
and before the database, as `icbm serve` does (ADR-0006). The production transports' sender-side
request lines land there beside the ledger's reservations. Turning the log on sends nothing and
changes no manifest, ceiling or ledger row.

A campaign armed and approved before this change — `m3-accept-01` at
`7ab7154d091b50ecb275955a98184bd8a5bc08a6` — cannot run on the fixed code, whose SHA differs. It is
kept as it is, and by that ruling the replacement campaign starts over with its own id, root, M1
connection, arming and approval.

### 6.7 Campaign identity (Issue #52 ruling 5714750891)

**The ledger owns the id.** `init --root <dir> --campaign-id <m3-accept-NN>` is the only command
that names a campaign. The new ledger writes the id into its INITIALIZED event, so the id is durable
before anything is armed; `CampaignLedger.campaign_id()` reads it back. `arm`, `approve`, `status`,
`run-pass` and `closeout` take no id and compare against no constant: each reads the ledger under
`<dir>`. An id has the form `m3-accept-NN`. The replacement campaign is `m3-accept-02`.

**Everything derived from it uses that id.** The target digest is
`sha256("<campaign id>\n<canonical URL>")` and the approval phrase is
`APPROVE <campaign id> <12 hex of the armed SHA> TWO-PASS-REAL`, so one URL and one SHA under two
campaign ids give two target digests, two manifest digests and two phrases. The ledger builds the
manifest itself when it is armed — its `campaign_id` and its target digest both from its own id —
so no caller can arm a ledger under another id. The armed-target PREP gate (§6.6) digests with the
same function and the same id. Closeout reports the ledger's id. A ledger whose manifest names
another campaign than its INITIALIZED event is refused: it has no identity to act on.

**The first campaign, read as it is.** `m3-accept-01` was created before the id was recorded: its
INITIALIZED event is empty, and its schema pins the id in a CHECK. For such a ledger, and only when
it was armed, the manifest's `campaign_id` stands in. Nothing is written back to it — no backfill, no
migration, no re-arm — and the digest formula is the one it was armed with. On any SHA but
`7ab7154d091b50ecb275955a98184bd8a5bc08a6` its exact-SHA PREP gate refuses it. New ledgers keep
the manifest's `campaign_id` column with a non-empty length check instead of the pinned value.

### 6.8 Image reference diagnostics (Issue #52 ruling 5716978033, PR-1)

`m3-accept-02` PASS-A ended in a terminal HOLD because one product image reference (`DETAIL:16`,
`km.aux.photoslide`) was recorded `FETCH_FAILED` with no request sent. The revision could not say
why. It recorded no locator for any reference that produced no bytes, whatever its URL looked like,
so a missing locator is **not** evidence of that URL's shape, and the cause of `DETAIL:16` is not
established by this change. PR-2 reproduces it separately. The acceptance model is unchanged and the
HOLD stands.

What a revision now keeps apart, for every image reference:

* **How the page wrote it.** `source_form` is `ABSOLUTE`, `PROTOCOL_RELATIVE` or `RELATIVE`, and
  `source_trimmed` says whether surrounding whitespace was trimmed before the reference was resolved.
  The written text is used in memory only, because it may carry a token or credentials
  (ADR-0010 §9).
* **What it resolved to.** `locator` is the canonical fetch target as the transport's target check
  computes it — https, host as parsed, path as written — when that target is allowed and carries no
  query. It is recorded whether or not bytes then arrived.
* **Why the target was refused.** `target_refusal` is one reason from a closed vocabulary:
  `UNPARSEABLE`, `WHITESPACE`, `FRAGMENT`, `NOT_ABSOLUTE`, `NON_HTTPS`, `UNSUPPORTED_SCHEME`,
  `CREDENTIALS_PRESENT`, `NON_STANDARD_PORT`, `HOST_NOT_ALLOWLISTED`, `PATH_NOT_ALLOWED`,
  `QUERY_NOT_ALLOWED`. There is no catch-all. A URL with several defects gets the first in that fixed
  order, so the same URL always gets the same reason. A refused reference is `REVIEW_REQUIRED`
  (`FETCH_FAILED`) with no bytes and no locator, and nothing is reserved or sent for it.

There is one judge of fetchability: the COLLECT transport's target check (`image_fetch_target` /
`check_target`). Generic COLLECT core asks it before a request, and the gateway asks it again. No
URL is repaired: no http→https, no fragment, credential or port removal. Host, scheme, port,
redirect and budget policy are unchanged. A supplier parser only reports what the page wrote beside
what it resolved to. The KM parser's roles, order and resolved URLs are unchanged, so
`EXTRACTOR_REVISION` stays `kmretail-1` and only its byte fingerprint is re-pinned.
References recorded before migration `0011` read back with these three fields `null`.

### 6.9 Image acceptance model (Issue #52 ruling 5723016554)

`m3-accept-03` PASS-A proved `DETAIL:16` is `source_form = ABSOLUTE` with
`target_refusal = NON_HTTPS`: the page itself wrote an absolute `http://` reference, and nothing was
requested for it. `m3-accept-03` stays HOLD. The model below applies to revisions recorded from now
on. It changes no stored revision and no campaign verdict.

**Two axes, never one status (R1).** Every reference is decided when its revision is recorded:

| certainty | disposition | when |
|---|---|---|
| `DETERMINATE` | `INCLUDED` | its bytes were observed and stored |
| `DETERMINATE` | `EXCLUDED` | a row of the closed exclusion table names what the page wrote and what the transport refused |
| `INDETERMINATE` | `UNRESOLVED` | everything else |

**The closed exclusion table (R2, R3, R11, R13).** It has one row:

| written form | transport refusal | exclusion |
|---|---|---|
| `ABSOLUTE` | `NON_HTTPS` | `SOURCE_AUTHORED_NON_HTTPS` |

The row also needs the reference to be `FETCH_FAILED`, with no bytes and no locator, and the form
must have been reported. A pair that is not a row stays `UNRESOLVED`. That includes:

* `NOT_ABSOLUTE` in any form, which can be a parser regression (R3);
* `NON_HTTPS` after ICBM resolved a relative or protocol-relative reference;
* budget exhaustion, even when the reference would also have been refused (R4);
* every network, server and content failure (R5);
* host, path and query refusals, which can mean ICBM's profile is behind the source.

The table only reads what the transport recorded. It never parses, resolves, repairs or re-fetches
a URL, and there is no `OTHER` reason.

**The images field.** It is `ABSENT` when the source shows no image. Otherwise it is `CONFIRMED`
only when all of these hold:

1. no reference is `UNRESOLVED` (R7);
2. a `REPRESENTATIVE` reference is `INCLUDED`, and if the source exposed any `DETAIL` reference, a
   `DETAIL` one is `INCLUDED` too (R6). Which roles the source exposed is read from its references,
   never from which requests succeeded (R12);
3. excluded references are not more than one third of all references (R9). Every excluded
   position counts, even when several share a reason (R10). Exactly one third passes.

When these hold, exclusions alone do not lower the field (R8). Each guard that fails adds its own
`REVIEW_REQUIRED` evidence entry: `images:representative`, `images:detail` or `images:excluded`. An
excluded reference contributes `ABSENT` evidence with its reason, e.g.
`DETAIL:16:EXCLUDED:SOURCE_AUTHORED_NON_HTTPS`. Its image-reference row keeps its PR #74
diagnostics unchanged: `REVIEW_REQUIRED`, `FETCH_FAILED`, `target_refusal`, `source_form`, no locator
and no raw URL (R14).

**Where the decision lives.** Each reference's `certainty`, `disposition` and `exclusion`, plus the
model name `image-acceptance/v1`, are stored in the revision's own `images` field value. That value
is immutable and fingerprinted, so no schema change is needed. The read-back and API return these
fields exactly as recorded. A revision recorded before the model has none of them and reads back
with all three `null`. Nothing classifies it after the fact. The pass judge still holds on such a
revision's unobserved references exactly as it did before.

**The pass judge.** `classify_pass` uses the recorded decision. An `UNRESOLVED` reference is still
`IMAGE_REFERENCE_UNRESOLVED`. An `EXCLUDED` reference is only the observation
`IMAGE_REFERENCE_EXCLUDED:<count>:<reasons>`. Whether exclusions may be tolerated was already
decided by the images field, and reaches the verdict as `CORE_FACT_AMBIGUOUS:images` when they may
not.
